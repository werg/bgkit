# bgkit

bgkit gives a language model access to more text than fits in its context budget. A bidirectional
encoder reads a text together with a prompt that states what the reader needs, compresses it by a
chosen ratio, and projects the result into the decoder's input embedding space. The decoder reads
these vectors in place of the text's tokens, in a slot among ordinary tokens; one input can hold
any number of slots.

- **Paper:** [bgkit: Reading Compressed Context through a Language Model's Embedding Layer](paper/main.pdf)
- **Model:** [gabrielpickard/bgkit-350m](https://huggingface.co/gabrielpickard/bgkit-350m) on Hugging
  Face: a 350M encoder and a 350M decoder fine-tuned from Liquid AI's LFM2.5 models, adapters merged,
  with standalone inference code (`torch` + `transformers` only).

## Quick start

```python
import sys
from huggingface_hub import snapshot_download

path = snapshot_download("gabrielpickard/bgkit-350m")
sys.path.insert(0, path)
from modeling_bgkit import Bgkit

bg = Bgkit.from_pretrained(path, device="cuda")
print(bg.answer(context=long_text, question="Who founded the company?", budget=512))
```

See the [model card](release/huggingface/README.md) for the lower-level `compress` / `generate`
API, the slot format and the limitations.

## Results in brief

At a fixed number of decoder positions for the context, on nine long-context benchmarks, the compressed
context scores significantly above the same decoder reading truncated text in 16 of 26 settings and
above LongLLMLingua in 13 of 22. It is above BM25 retrieval where answers combine facts spread through
the context (BABILong, HotpotQA, MuSiQue), e.g. BABILong 0.79 in 512 positions against at most 0.38
for any text method in 2,048. At the encoder's own kept positions, its vectors score far above the
tokens there (0.74 against 0.26 on BABILong 16k). With the same decoder weights, the compressed context also scores above the
entire untruncated text on BABILong, HotpotQA and LoCoMo (e.g. HotpotQA 0.64 against 0.36). Exact strings are not preserved (RULER, where BM25
does better). Over a 110k-token context the decoder needs 0.1 GB instead of 5.0 GB beyond its weights;
the encoder pass costs about as much compute as a full-context prefill. Details, baselines and
limitations are in the paper.


## Reproducing

Training and GPU evaluation run in the Docker image built from `docker/Dockerfile` (NGC PyTorch;
developed on an NVIDIA DGX Spark). Storage paths come from a `.env` file at the repository root
(`cp .env.example .env`).

| Step | Command |
|---|---|
| Train the released model's final stage | `docker compose -f docker/docker-compose.yaml run --rm train-bgkit2-s2` |
| Prepare benchmark items | `python scripts/bgkit2_bench_prep.py --bench babilong,ruler,quality,narrativeqa,hotpot,musique,longmemeval,locomo --out-dir <dir>` |
| Run a benchmark | `python scripts/bgkit2_bench.py --experiment bgkit2_s2_showcase --checkpoint <ckpt> --items <bench>.jsonl --budgets 256,512 --arms bgkit,text,base --out <out>.json` |
| LLM-judge scoring | `python scripts/bgkit2_bench_judge.py --url <judge server> --run-dir <dir> --bench <bench> --items <bench>.jsonl` |
| Paper tables | `python scripts/bgkit2_paper_tables.py` |
| Export to Hugging Face format | `PYTHONPATH=src python scripts/bgkit2_export_hf.py --experiment bgkit2_s2_showcase --checkpoint <ckpt> --out <dir>` |

The released model ends a chain of warm-started runs (see the paper's training section and
`configs/experiment/`); the final stage alone does not reproduce it from scratch.

CPU unit tests: `uv sync --extra dev && .venv/bin/pytest tests/unit -v`.
